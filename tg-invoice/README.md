# TG Invoice

**TG Invoice** (brand **tgeasy**) is a production-quality, multi-tenant SaaS invoicing app for small businesses. Each business gets its own isolated workspace: customers, products, quotations, invoices, payments, receipts, reports, team members, branding and numbering — all enforced server-side.

Guests can register and create their first business immediately, then send professional quotations, convert them to invoices, record payments that generate receipts, and watch reports and dashboards update from server-calculated figures.

> JavaScript end-to-end. No TypeScript, no mock data — every number in the UI is calculated by the API from rows in PostgreSQL.

The UI is built from a small set of Tailwind v4 design tokens declared once in `frontend/src/index.css` (`@theme` + `@layer components`) and reused everywhere, so the look stays consistent:

The layout leans on **light-blue cards** (KPI tiles, toolbars, table headers, form banners) and a **rich blue gradient sidebar** (`brand-600 → brand-700 → brand-800` with ambient glows, white active pills and light-on-blue labels). The marketing/landing and auth screens layer their content over a bundled, license-free **business/invoicing background photo** (`frontend/src/assets/invoice-bg.jpg`) with lightened gradients so the photo stays visible while text remains readable. ### Motion

Animations are declared once as `--animate-*` tokens with `@keyframes` in `index.css`, then applied through utility classes (`animate-fade-in`, `animate-fade-up`, `animate-scale-in`, `animate-slide-in-right`, `animate-pop`, `animate-float`, `animate-shimmer`):

- **Page transitions** — the app shell keys `<main>` on the route so every navigation plays a soft `fade-up`.
- **Sidebar** — nav items stagger in on mount; rows nudge right and icons scale on hover; active items are white pills with depth.
- **Overlays** — modals scale in over a fading backdrop, toasts slide in from the right, buttons press down slightly.
- **Reveal** — the `Reveal` helper (`ui.jsx`) fades + lifts sections into view on first scroll via `IntersectionObserver`.
- **Loading** — `LoadingBlock` renders shimmer skeletons instead of a bare spinner.

All motion is disabled under `prefers-reduced-motion: reduce`.

### PWA & mobile

TG Invoice is designed **mobile-first** — it is meant to be used on a phone (Android, iOS) and installed like a native app.

- **Installable.** `frontend/public/manifest.webmanifest` (name, standalone display, theme colour, app shortcuts for *New invoice / New quotation / Customers / Reports*) plus a 192/512/maskable/`apple-touch-icon` icon set generated by `frontend/scripts/generate-icons.mjs` (dependency-free — run `node scripts/generate-icons.mjs` after a brand change).
- **Offline app shell.** `frontend/public/sw.js` registers in production builds only. Navigations are network-first with a cached fallback, hashed assets are stale-while-revalidate, and `/api/*` is **never** cached so financial figures are always live.
- **In-app install button.** When the browser exposes `beforeinstallprompt`, an *Install app* button appears in the sidebar (`useInstallPrompt`); iOS users install via Share → *Add to Home Screen*.
- **Mobile chrome.** A bottom tab bar (Home · Invoices · Customers · Reports · More) shows below `lg`, the drawer opens from *More*, and safe-area insets (`viewport-fit=cover` + `env(safe-area-inset-*)`) keep content clear of notches and home indicators. Wide data tables scroll horizontally rather than overflowing.
- **To try the PWA locally:** `cd frontend && npm run build && npm run preview`, then open the preview URL on your phone (same network) or in DevTools' device mode → **Install**.

## 3. Quick start (local development)

### Prerequisites

- Node.js **18+** (developed on v25)
- PostgreSQL **14+** running locally (developed on PostgreSQL 16)

### 1. Install dependencies

```bash
cd tg-invoice/backend
npm install

cd ../frontend
npm install
```

### 2. Create the database

```bash
createdb tg_invoice        # or: psql -U postgres -c "CREATE DATABASE tg_invoice;"
```

### 3. Configure environment

```bash
cd backend
copy .env.example .env     # Windows
# cp .env.example .env     # macOS / Linux

cd ../frontend
copy .env.example .env
```

Set `DATABASE_URL` in `backend/.env` to your local database and set both JWT secrets to long random strings. See section 5 for every variable.

### 4. Run migrations and seed demo data

```bash
cd backend
npx prisma migrate deploy     # apply versioned migrations
npx prisma generate           # generate the Prisma client
npm run db:seed               # seed Zarox Energy + ABC Engineering demo businesses

# Optional: fill every tenant with rich sample data you can delete later
npm run db:demo               # customers, products, quotations, invoices, payments, receipts
```

> **Deletable demo data.** `npm run db:demo` marks everything it creates with `isDemo = true` and refreshes itself on every run (no duplicates). When you no longer want it, `npm run db:clear-demo` removes **only** those records — real, hand-entered data is never touched. See section 6.

### 5. Start both apps

```bash
# terminal 1
cd backend
npm run dev        # http://localhost:5050

# terminal 2
cd frontend
npm run dev        # http://localhost:5173
```

Open <http://localhost:5173> and sign in with a demo account (section 6).

> **Port note.** This project is configured to run the API on **5050** locally because port 5000 is held by a Windows system service on the development machine. `.env.example` keeps the conventional `5000`; `.env` overrides it. In production (Render) the platform-provided `PORT` is used.

### Platform administrator (super-admin)

A super-admin is a platform operator who oversees **and manages** every business without belonging to one. It is a single boolean on the `User` model (`isPlatformAdmin`) that **no tenant-facing flow can ever set** — it is granted by the bootstrap script below, or by another existing platform admin from `/admin`:

```bash
cd backend
npm run db:superadmin -- super@tginvoice.com            # create + grant (dev default password)
npm run db:superadmin -- super@tginvoice.com 'MyStrongPass!'   # promote + set password
npm run db:superadmin -- super@tginvoice.com --name="Super Admin"
npm run db:superadmin -- super@tginvoice.com --revoke   # remove admin access
```

- If the account does not exist it is created; if it exists it is promoted in place (password untouched unless one is given). Running the script also forces the account back to `ACTIVE`, so a suspended super-admin can always be recovered from the server.
- New accounts default to `ChangeMe123!` — **change it immediately after first sign-in** in any shared/production environment.
- The `super@tginvoice.com` bootstrap used in this repo's dev database has **no business membership by design**: signing in lands on **`/admin`** (Platform overview), not the tenant dashboard.
- **`/api/admin/**`** endpoints run `requireAuth` + `requirePlatformAdmin` and are deliberately **not tenant-scoped**. Reads expose only aggregates and directory rows; writes are limited to platform-level controls and **never touch a tenant's documents**:
  - **Register a business** (`POST /api/admin/tenants`) — creates an isolated workspace (settings + document sequences) and can attach an already-registered account as its `OWNER`. With no owner the business is created owner-less and can be granted access later.
  - **Edit business details** (`PATCH /api/admin/tenants/:id`) — name + contact info.
  - **Suspend / reactivate a business** (`POST .../suspend`, `.../activate`) — a suspended business is unreachable by **all** of its members (`requireTenant` returns `403`, it disappears from their business list) while its data is kept intact.
  - **Manage tenant admins** (`POST .../members`, `DELETE .../members/:userId`) — grant a registered account `OWNER`/`ADMIN` access to a business, or remove them. Tenant **staff** are intentionally out of scope here: they are the tenant admin's concern, managed from the business's own **Team** page. The last active owner of a business cannot be revoked. (`STAFF` is rejected with `400`.)
  - **Suspend / reactivate an account** (`POST /api/admin/users/:id/suspend|activate`) — suspension revokes every refresh token (immediate sign-out) and blocks sign-in; a suspended token is refused with `403`.
  - **Platform users directory** (`GET /api/admin/users`) — lists **platform operators only** (`isPlatformAdmin` accounts). Tenant staff and end-users never appear here.
  - **Add a platform operator** (`POST /api/admin/users`) — promote an existing account (by email) to platform admin, or create a brand-new operator account and return a **one-time temporary password** (never emailed) for the super-admin to pass on securely. An already-admin email returns `409`.
  - **Grant / revoke platform-admin access** (`PATCH /api/admin/users/:id/platform-admin`) — promote another operator or stand them down. A platform admin cannot suspend or demote **themselves**.
  - Every action is written to the affected business's audit trail (`CREATE_TENANT`, `SUSPEND_TENANT`, `GRANT_ACCESS`, `SUSPEND_USER`, …).
  - A regular tenant admin gets `403` from every `/api/admin/*` route.
- A **platform-wide status** lives on `Tenant.status` and `User.status` (`ACCOUNT_STATUS`: `ACTIVE` / `SUSPENDED`). `requireAuth` refuses suspended accounts; `requireTenant` refuses every member of a suspended business.
- The frontend route `/admin` is guarded by `RequirePlatformAdmin`; a normal user is redirected to `/dashboard`. Super-admins who also own tenants see a **Platform Admin** entry in the sidebar. A suspended member is dropped from `/api/tenants` and `/api/auth` automatically.

### Notifications

TG Invoice ships a **persistent, per-user notification centre** — a bell in every top bar (the tenant app and `/admin`) with an unread badge, a dropdown, and mark-as-read. Notifications are stored server-side (the `Notification` model, scoped to the recipient `userId`) and polled every 30s + on window focus, so there is **no socket dependency**.

- **Endpoints** (authenticated, and deliberately **not tenant-scoped** — a notification belongs to a person, not a business): `GET /api/notifications` (list + `meta.unread`), `GET /api/notifications/unread-count`, `POST /api/notifications/:id/read`, `POST /api/notifications/read-all`. Every query is scoped to `req.user.id`, so a notification id can never be read or mutated across accounts.
- **Delivery is event-driven** through `notificationService.notify*()`: it writes the rows and, when SMTP is configured, emails the recipients **fire-and-forget** — a failed notification or email can never break the operation that triggered it.
- **Events**: platform actions notify the affected people — business suspended/activated → that business's tenant admins; access granted/revoked and platform-admin granted/revoked → the target account; account suspended/activated → the account holder. Tenant actions — payment received and team member joined → the business's tenant admins (excluding the actor).

## 7. Multi-tenant isolation

Isolation is enforced **on the server**, never trusted from the client.

- **Every request flows through three layers** before a controller runs: `requireAuth` (verifies the JWT) → `requireTenant` (reads `X-Tenant-Id`, looks up the caller's **Membership** in that tenant, rejects with `403` if there is none) → optional `requireRole` / `requireAdmin`.
- A forged or missing `X-Tenant-Id` is treated identically: **no membership, no access**.
- Controllers **never** take a tenant id from the body or query. They use `req.tenant.id` and scope every query with `where: { id, tenantId }` / `tenantId`, so a correctly-guessed id in another tenant returns `404` rather than leaking data.
- Numbering is per-tenant via `DocumentSequence` rows updated inside transactions, so two businesses can both issue `INV-00001`.
- Logos, settings, audit logs and search are all tenant-scoped.
- The only authenticated-exempt route is the **public document link** (`/api/public/documents/:token`); it never trusts a header — it re-derives the tenant from the signed token and scopes the query to that tenant, and it can only ever read the single document named in the token.

This is covered by the automated suite in `backend/test/` (`npm test`): 11 tests assert that one tenant can never read, update, delete, pay, search or switch into another tenant — including via a forged tenant header — while both tenants can independently use the same document numbers.

### Roles

| Role | Capabilities |
|------|--------------|
| `OWNER` | Everything, including team and settings. Cannot be removed or have their role changed. |
| `ADMIN` | Everything except ownership: settings, team management, documents, reports, audit. |
| `STAFF` | Works on documents (customers, products, quotations, invoices, payments, receipts) and views reports. **Settings mutations, team management and audit logs return `403`** — enforced by `requireAdmin` in the router and mirrored by the UI. |

## 8. Financial correctness

- All money is stored as PostgreSQL `Decimal(14,2)` (major units) and every calculation is performed in **integer minor units** inside `src/utils/money.js`. The frontend mirrors line maths in `src/utils/lineMath.js` only for live preview, and **the server always recalculates** totals, tax, discounts, balances and statuses on save.
- Document status is derived server-side (`deriveInvoiceStatus`): `CANCELLED` / `VOID` → `DRAFT` → `PAID` → `OVERDUE` → `PARTIALLY_PAID` → `SENT` → `UNPAID`. Recording a payment can flip an invoice to *Paid* immediately.
- Invoices, quotations and receipts each get a per-tenant number from `DocumentSequence` (`INV-`, `QT-`, `REC-` prefixes configurable in Settings; customer codes `CUS-`).
- **Voiding / cancelling** an invoice keeps its number and history but removes it from totals and outstanding balances.

## 10. Feature walkthrough (what to try)

- **Registration & onboarding** — `/register` creates the account *and* the first business; the onboarding wizard (`/onboarding`) prefills from the server and can be skipped. The business switcher creates additional businesses.
- **Quotations** — create with line items, discounts and tax; preview the client-facing document; change status; **convert to invoice** in one click.
- **Invoices** — create/edit, record payments (partial or full), cancel/void, download/print PDF, share via WhatsApp or email, each with a signed **public "view online" link** the client can open without an account.
- **Type-and-go line items** — you don't have to pre-create a catalogue. Type a description and price straight into a quotation or invoice and it's saved to **Products & services** automatically for next time (case-insensitive de-duplication means re-typing never makes duplicates). Untick *Save new items to Products & services* on the form to keep a one-off line out of your catalogue.
- **Public document links** — every share (WhatsApp/email) includes an unguessable, expiring URL (`/api/public/documents/:token`) that renders that one document as an inline PDF. Tokens are HMAC-signed and scoped to a single document + tenant, so they cannot be forged or enumerated, and tampered/expired links return `410 Gone`. On a phone the WhatsApp button opens the installed WhatsApp app; on desktop it uses `wa.me`.
- **Receipts** — generated automatically from each payment, with amount-in-words, payment details and PDF.
- **Customers & Products** — full CRUD, search, filters, and a customer detail page with lifetime invoiced/paid figures.
- **Reports** — Invoices, Payments, Quotations and Customers tabs, each with a date-period filter (today / this week / this month / last month / this year / custom / all time), server-computed summaries and CSV export.
- **Team** — invite by email with a role, resend/revoke invitations, change roles, deactivate or remove members (owner/admin only).
- **Notifications** — the bell in the top bar carries an unread badge; open it to see events (payment received, team member joined, and platform account/business changes), then mark one or all as read. Key events also send an email when SMTP is configured.

- **Installable PWA** — open the app, choose *Install app* (Android/desktop) or Share → *Add to Home Screen* (iOS); it launches standalone with an offline app shell. The sidebar hides the button once installed.

## 11. Deployment guide

The app deploys as three pieces: **Neon** (database) → **Render** (API) → **Vercel** (frontend).

### 11.1 Database — Neon

1. Create a project at <https://neon.tech> and copy the **pooled** connection string (it ends with `?sslmode=require`).
2. From your machine, point `DATABASE_URL` at Neon and apply migrations:
   ```bash
   cd backend
   DATABASE_URL="postgresql://…neon…?sslmode=require" npx prisma migrate deploy
   ```
   (Add `npm run db:seed` if you want the demo businesses in the cloud too — skip for a clean production database.)

### 11.2 API — Render

1. New **Web Service** → connect the repository → **Root Directory:** `backend`.
2. Build command: `npm install && npx prisma generate && npx prisma migrate deploy`
3. Start command: `npm start`
4. Environment variables:
   ```
   DATABASE_URL       = <Neon pooled connection string>
   JWT_SECRET         = <long random string>
   JWT_REFRESH_SECRET = <different long random string>
   JWT_ACCESS_EXPIRES = 15m
   JWT_REFRESH_EXPIRES_DAYS = 7
   NODE_ENV           = production
   FRONTEND_URL       = https://<your-vercel-app>.vercel.app
   PUBLIC_BASE_URL    = https://<your-render-service>.onrender.com
   SHARE_SECRET       = <long random string, distinct from JWT secrets>
   SHARE_LINK_DAYS    = 30
   SMTP_*             = <optional>
   STORAGE_DRIVER     = local
   ```
   Do **not** set `PORT` — Render provides it.
5. Note: with `STORAGE_DRIVER=local`, uploaded logos live on the Render instance's disk. For durable uploads across deploys, configure an external bucket or add the cloud storage driver.

### 11.3 Frontend — Vercel

1. New Project → import the repository → **Root Directory:** `frontend`.
2. Framework preset: **Vite**. Build: `npm run build`. Output: `dist`.
3. Environment variable (Production + Preview):
   ```
   VITE_API_URL = https://<your-render-service>.onrender.com/api
   ```
4. Deploy, then update `FRONTEND_URL` on Render to the final Vercel URL and redeploy the API so CORS and email links match.

### 11.4 Post-deploy checklist

- `GET https://<api>/api/health` returns `{ "success": true, … }`.
- Register a fresh account and create a business (this exercises DB writes end-to-end).
- Sign in, create a customer, a quotation and convert it to an invoice.
- Download an invoice PDF.

## 13. Security summary

- Passwords hashed with **bcrypt** (cost 12).
- Access tokens are short-lived and kept **in memory** (not localStorage) to reduce XSS exposure; refresh tokens are rotated, single-use, and stored in an **httpOnly** cookie scoped to `path=/api/auth`.
- Changing a password revokes all of a user's refresh tokens.
- Tenant context comes only from a verified **Membership** — never from the client.
- Requests are validated with **Zod**; errors use a consistent `{ success, data }` / `{ success, error }` envelope.
- `helmet` security headers, CORS restricted to `FRONTEND_URL`, request-size limits and rate limiting are enabled.
- Audit logging records sensitive actions (invites, role changes, member removal, document changes) per tenant.
- `.env` files are git-ignored; `.env.example` documents the shape without secrets.
